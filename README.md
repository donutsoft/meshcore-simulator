# MeshCore Simulator

MeshCore Simulator captures traffic from a MeshCore companion over TCP, USB serial, or Bluetooth LE and turns observed three-byte repeater routes into a persistent topology graph. The graph is displayed with Leaflet and OpenStreetMap and is intended to become the input to desktop MeshCore routing simulations.

## Current milestone

- Connect to the companion TCP protocol, USB serial framing, or the MeshCore Nordic UART BLE service.
- Store every valid repeater advert, including its full public key and advertised GPS coordinates, in SQLite.
- Treat an advertised latitude/longitude pair of `0,0` as missing GPS data rather than a location at Null Island.
- Store other traffic only when its route uses three-byte repeater IDs. One- and two-byte paths are counted as ignored and never enter the packet tables.
- Resolve a three-byte repeater ID as the first three bytes of its advertised public key.
- Infer directed hearing observations from adjacent entries in a packet route. For a repeater advert, the advertising repeater is prepended to its observed route.
- Display the resulting undirected reachability graph over OpenStreetMap while retaining directional observations in SQLite and the API.
- Hide zero-link repeaters from the topology API and map while retaining them in SQLite until a route links them into the graph.
- Estimate a missing repeater position from the spherical geographic midpoint of all adjacent repeaters with known or inferred positions. Estimated nodes are visually distinct from GPS-backed nodes.

When many underconstrained repeaters resolve to the same midpoint (for example, a component with only one GPS advert), the map spreads those markers on a small deterministic spiral so links remain visible. Dashed links touch a visually spread node; the SQLite/API midpoint remains unchanged.

An edge means that two repeaters were adjacent in at least one received route. It is evidence of reachability, not proof that the radio link is currently available. The `directed_links` table preserves packet-order direction so later routing experiments can apply a different interpretation.

## Run

Python 3.12+ and [`uv`](https://docs.astral.sh/uv/) are recommended:

```bash
cd meshcore-simulator
uv sync
uv run meshcore-simulator
```

Open <http://127.0.0.1:8080> and connect a companion from the sidebar. No map account or API key is required.

### Attach two simulated companions

The map can start the native repeater simulation with two TCP companion-radio endpoints:

1. In **Simulated companions**, select the TCP 5000 slot and click a repeater marker.
2. Select the TCP 5001 slot and click a different repeater marker.
3. Set **Random packet drop rate** from 0% to 100%.
4. Click **Start simulation**.

The native target is built automatically when necessary. It then runs in real time until stopped and listens on `127.0.0.1:5000` and `127.0.0.1:5001`. Each TCP endpoint runs MeshCore's real `companion_radio/MyMesh` firmware and is in bidirectional radio range of its selected repeater and every direct neighbor of that repeater. Connect the MeshCore app using its TCP transport; normal device setup, contacts, channels, identity management, messaging, and asynchronous push frames are handled by the upstream companion implementation.

Every companion protocol frame is printed to the web-server terminal as uppercase hexadecimal with its port and direction. For example, `TCP_FRAME port=5001 direction=app_to_companion length=3 hex=01 02 FF`. These traces are unredacted and can contain encoded messages, keys, and configuration values.

The configured drop rate is applied independently to every otherwise eligible simulated radio reception. Collision losses are modeled separately and still occur when the random drop rate is 0%.

Repeater-to-repeater transmissions are highlighted on the map using a deterministic color derived from each packet's data hash, so a message and its ACK are visually distinct. Each edge appears when that radio transmission starts and is removed when its calculated LoRa airtime ends. Flood transmissions are shown on every compatible neighboring edge; direct transmissions show only the intended next repeater. A transmission remains visible for its on-air interval even if it ultimately collides or is randomly dropped.

The simulation panel displays cumulative bytes sent for each packet data hash. Each radio repeat adds that transmission's full packet length; a single flood transmission is counted once even though it is highlighted on every compatible neighboring edge. Transmissions are counted even when no neighboring repeater is eligible to receive them.

Companion identities are normal Ed25519 keypairs generated by MeshCore. Each endpoint has an isolated persistent filesystem image, so its identity, settings, and contacts survive app reconnects and simulator restarts.

You can also select one startup transport:

```bash
uv run meshcore-simulator --tcp meshcore.local --tcp-port 5000
uv run meshcore-simulator --usb /dev/cu.usbmodem101
uv run meshcore-simulator --ble DEVICE_ID
```

Import saved repeater adverts from `meshcore-security` into SQLite:

```bash
uv run meshcore-simulator \
  --import-adverts ../meshcore-security/captures/adverts.jsonl \
  --import-only
```

Imports are idempotent: an observation with the same reception time, public key, and raw packet is stored only once. Only repeater adverts are imported; companion and room adverts are skipped. A three-byte prefix collision is reported and skipped rather than associating the wrong public key.

Useful options:

```text
--database PATH       SQLite path (default: data/meshcore.sqlite3)
--web-host HOST       dashboard bind address (default: 127.0.0.1)
--web-port PORT       dashboard port (default: 8080)
```

The default interactive map uses OpenStreetMap's public raster tile service with visible attribution. Follow the [OpenStreetMap tile usage policy](https://operations.osmfoundation.org/policies/tiles/) and do not bulk-download or prefetch those tiles. For larger deployments, configure another OpenStreetMap-compatible tile provider:

```bash
export MESHCORE_TILE_URL='https://your-provider.example/{z}/{x}/{y}.png'
export MESHCORE_TILE_ATTRIBUTION='Map data attribution'
uv run meshcore-simulator
```

## SQLite model

- `repeaters`: one resolved or route-only three-byte repeater ID, with latest known identity and GPS metadata.
- `advert_observations`: append-only log of every valid repeater advert.
- `packets`: raw packets whose encoded path hash size is exactly three bytes.
- `packet_hops`: ordered route entries for each logged packet.
- `directed_links`: aggregated ordered adjacency observations.

SQLite uses foreign keys and WAL mode. The topology endpoint is `GET /api/topology`.

## Repeater simulation

The upstream MeshCore source is vendored in `MeshCore/` and includes a macOS host target. Every SQLite repeater row instantiates the real upstream `examples/simple_repeater/MyMesh` class, while each TCP endpoint instantiates the real `examples/companion_radio/MyMesh` class. Board, clock, storage, and TCP adapters provide the host environment; a central in-memory radio medium is the replacement for LoRa and treats every `directed_links` observation as a bidirectional radio edge.

Each repeater receives a normally generated Ed25519 identity, then its first three public-key bytes are replaced with the observed `repeater_id` from SQLite. Because that forced prefix no longer corresponds to the generated private key, the host build bypasses advert signature verification only for the explicitly registered forced repeater identities. Companion identities and all other identities continue through MeshCore's normal Ed25519 implementation.

Build, test, and run it with:

```bash
make -C MeshCore/simulator test
MeshCore/simulator/build/meshcore-repeater-sim \
  --database data/meshcore.sqlite3 \
  --duration-ms 10000 \
  --interference 0.02 \
  --seed 42
```

The first connected repeater injects a flood advert unless one or more `--inject REPEATER_ID@MILLISECONDS` options are supplied. Observed links are symmetric by default because the stored order describes an observation, not a one-way radio edge. `--links directed` remains available as an explicit diagnostic override. Radio options include `--frequency`, `--bandwidth`, `--sf`, `--cr`, and `--preamble`. The simulator computes LoRa time-on-air for every packet and uses those intervals for transmit completion, receiver-specific and hidden-terminal collisions, and half-duplex loss. Receivers only decode transmissions with compatible LoRa channel parameters.

See [`MeshCore/simulator/README.md`](MeshCore/simulator/README.md) for the model and all options.
